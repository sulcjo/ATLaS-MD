## Adaptive-production epoch loop can stop after 1 epoch regardless of `--ap-epochs` — FIXED 2026-07-27

- Root-caused why run configured `ap_epochs: 2` (torsion-pca epoch 0 → tica-linear epoch 1) only produced real samples in `epoch_000`, `epoch_001/` holding just stray planning CSV, rest of MD-pool budget going to `final/baseline` + `final/topup_*`.
- `run_adaptive_production_auto_loop` (`gareus/adaptive_production.py`) runs convergence gate after every epoch (`status`/`stop_adaptive` computed ~line 5288): no errors, no `continue_reasons` (state below `convergence_min_samples_per_state`, default 50 — trivially cleared by any real epoch — or proposed add/split action, impossible once at window cap), no warnings → `status="converged"`, `stop_adaptive=True` unconditionally. Loop used to `break` on that regardless how many epochs `--ap-epochs` still allowed. Confirmed: `adaptive_production/epoch_000/adaptive_convergence_gate.json` had `{"status": "converged", "stop_adaptive": true, "continue_reasons": []}`.
- Same pattern independently seen on different real run (`chignolin_sigma3_2d`): epoch 0 converged trivially, jumped to final, final phase's own (stricter) quality gate then demanded more discovery epochs via manual `--extend adaptive` re-invocation — early exit didn't save work, meant paying for final phase twice.
- tICA CV2 switch itself **not** at risk — tied to tICA refit succeeding at end of whichever epoch triggers `tica_update_after_epochs`, independent of adaptive loop's convergence-based early exit. Confirmed: `final/baseline`, `final/topup_001_12000`, `final/topup_002_31000` all ran with `secondary_cv: tica-linear` in `run_manifest.json` even though `epoch_001` (the "supposed" tica-linear epoch) never ran.
- Fix: convergence no longer breaks loop. `run_adaptive_production_auto_loop` now logs, falls through to next scheduled epoch; loop always runs full configured `adaptive_production_epochs` budget, only proceeds to final phase once exhausted. Adjacent `require_convergence_before_final` check (previously unreachable when converged, since break fired first) got explicit `not gate_converged` guard — extracted into `_epoch_loop_missing_convergence(epoch, max_epochs, gate_converged, require_convergence_before_final)` — so legit-converged last epoch doesn't spuriously raise. Tests: `tests/test_epoch_loop_convergence_guard.py` (truth table over epoch/max_epochs/convergence/policy combos, incl `max_epochs == 1` + last-epoch edge cases).
- Note `--ap-*` doesn't expose `require_convergence_before_final` at all (`gareus/cli.py`'s `_apply_v2_compat_shims` hardcodes it `False`, same "dropped tuning knob" pattern as `--ap-epoch0-step-fraction` before that flag) — so `RuntimeError` branch this guards can never fire from shipped CLI. Not fixed; flagging in case future `--ap-require-convergence-before-final`-style flag added, since guard's correctness matters then.


## Union-MBAR reduced-bias matrix was 100% NaN — `gareus_metadata.json` never has temperature field — FIXED 2026-07-27

- Found on real multi-day production run (`chignolin_sigma3_2d`): `adaptive_union_mbar.npz`'s `umbrella_bias_kcal_mol_nk`/`umbrella_bias_kj_mol_nk` 100% finite (sane 0-44 kcal/mol range) but `umbrella_reduced_bias_nk` 100% NaN despite real `N_k` sample counts (49,044 samples across 25 states) — `adaptive_union_mbar_analysis.json` errored with `"no finite samples remain after filtering"`.
- Root cause: `_metadata_beta_1_over_kj_mol` (`gareus/adaptive_production.py`) resolved `beta` by reading `temperature_K`/`temperature_k` from each run dir's `gareus_metadata.json` — but that file only holds CV/window bookkeeping (confirmed: 63 keys, zero temperature-related, across every subdir in real run). So `beta` was `None` for every merged sample row, `beta_1_over_kJ_mol` written `""` throughout campaign, `build_union_state_mbar_inputs`'s `umbrella_reduced_bias_nk = beta * umbrella_bias_kj` fell into `np.full_like(..., np.nan)` branch every time.
- Fix: added `resolve_run_temperature_k(run_dir)` to `gareus/io.py` — falls back to `run_manifest.json`'s `resolved_args.temperature_k` / `method_settings.temperature_k` (always populated by `gareus/provenance.py` for every run dir) when `gareus_metadata.json` has nothing usable. `_metadata_beta_1_over_kj_mol` now delegates to it.
- Same root cause silently hit `gareus/analysis.py`'s `_ensure_analysis_arrays_npz` (used reconstructing `analysis_arrays.npz` from Parquet for resumed/incomplete runs): read same never-populated `gareus_metadata.json` field but, unlike adaptive-production path, defaulted to `300.0 K` instead of failing — silently wrong (not NaN) for any run not at 300 K. Fixed to use same `resolve_run_temperature_k` helper; only defaults to 300 K (with printed warning) if helper finds nothing.
- Tests: `tests/test_resolve_run_temperature.py` (shared helper directly), `tests/test_beta_metadata_fallback.py` (adaptive-production wrapper, integration-level check).


## Union-MBAR bias matrix used stale global registry snapshot for every epoch — FIXED 2026-08-04

- Found answering question on how `analyze_gareus_mbar.py` handles mid-run secondary-CV redefinition (torsion-pca → tica-linear tICA auto-switch) for "united" PMF. Confirmed real, severe on live run (`chignolin_5`, epoch_000 torsion-pca → epoch_001+final tica-linear).
- Root cause: `load_parquet_adaptive_union` (`analyze_gareus_mbar.py`) rebuilt every sample's reduced bias energy (`u_nk`) using **one static snapshot** of window params — `final_registry_used_for_mbar.csv`/`state_registry.csv` — applied uniformly to state's samples across *every* epoch. Snapshot reflects state's *current* `primary_center`/`primary_k`/`secondary_center`/`secondary_k` — but those fields get overwritten in place whenever state recentered (e.g. `_apply_tica_centers_to_registry`, `gareus/adaptive_production.py`, fires on tICA CV2 auto-switch). Any earlier epoch's samples, collected under old center, then got bias energy rebuilt against new one.
- Measured on chignolin_5's real state 0: epoch_000 samples collected under `secondary_center=-2.1337` (`epoch_000/epoch_window_map.csv`, written once, never touched again); live registry (used every epoch under old code) held `+1.1632` post-switch. For 115,923 real epoch_000/state-0 samples, mean reconstructed reduced bias energy dropped 126.25 (buggy) → 2.49 (fixed) — ~124 kT spurious bias energy per sample, i.e. those samples got ≈0 MBAR importance weight in own generating state. 27/28 registry states got this overwrite when switch fired.
- Fix: each epoch's own `epoch_window_map.csv` already records window params actually in effect — `_load_epoch_task` now also parses `primary_center`/`primary_k`/`secondary_center`/`secondary_k` from it (previously only `state_id` kept), union bias matrix built **per-epoch-block** using native params (`_epoch_bias_param_vectors`, `_reconstruct_union_bias_block`), falling back to global snapshot only for states absent from given epoch's map (states born in later epoch — only case global row correct, only option). `beta` resolution moved to dedicated pre-pass so fixed before any per-epoch block built, rather than resolved lazily mid-loop (previously order-dependent, could in principle race downstream top-level beta fallback against already-built-but-wrong-beta block).
- End-to-end real-run verification (`chignolin_5`, full `analyze_gareus_mbar.py` re-run, same flags, before vs after): base MBAR ESS 67,198 (1.07% of 6.29M) → 360,438 (5.73%) — 5.4x more effective samples, expected once ~65-125 kT spurious bias energy stops crushing importance weights. PMF span 17.76 kcal/mol (inflated by corrupted bias energies) → 4.55 kcal/mol. MBAR convergence, window overlap (measured from raw CV samples, not `u_nk`) unchanged, as expected.
- **Any adaptive-production run whose CV2 (or CV1) window params ever recentered mid-campaign, analyzed through Parquet union path, has wrong PMF from this bug** — not just runs hitting tICA CV2 type-switch. Re-running `analyze_gareus_mbar.py` on such runs changes `pmf_summary.json`'s `mbar.base_ess`/`pmf_span_kcal_mol`/`pmf_minimum_cv_A`; don't treat prior results comparable without re-running.
- Separately, orthogonal to `u_nk` correctness: pooling raw `cv2` values from two different secondary-CV **projections** (torsion-pca vs tica-linear = different linear combos of same raw torsion features, not recentering of one coordinate) into single "secondary_cv" axis conflates two order parameters for any CV2-facing plot. `run_secondary_cv_analyses` now detects regime change via each epoch/phase's `run_manifest.json` (`_secondary_cv_epoch_regime_masks`), splits `analyze_secondary_cv_pmf`/`analyze_cv1_cv2_2d_fes` accordingly: regime containing run's *last* epoch/phase ("dominant") keeps existing unmodified output paths (all epochs pooled — correct, share one CV2 def); any earlier, different-regime epoch (e.g. `epoch_000` under torsion-pca before chignolin_5's tICA switch) gets own output under `secondary_cv_regime_<type>/` instead of silently pooled into united plot. Single-regime runs (vast majority) unaffected — `_secondary_cv_epoch_regime_masks` returns `None`, wrapper degrades to original calls, same paths. Doesn't touch MBAR's `f_k`/weights (already correct after `u_nk` fix) — only which samples' `cv2` values binned together for CV2-facing plots.
- Considered, not built: reprojecting epoch_000's raw torsion features through final tica-linear model (`project_tica1`) to harmonize pre-switch samples onto one common CV2 axis instead of plotting separately. Rejected after measuring real coverage: chignolin_5's `epoch_000/tica_obs/dihedral_obs_*.npz` covers only 7,668 of epoch_000's 731,754 real production samples (~1%), concentrated in narrow 127k-step window near epoch end rather than spread across it — harmonizing off that buffer would produce "unified" axis ~99% NaN for epoch_000, i.e. fabricate appearance of fix. Full-coverage version would need recomputing backbone torsion features from `replica_trajectories/*.xtc` directly (`backbone_dihedral_features` + torsion indices from `tica_state.json`) — real trajectory pass over ~730k frames × 27 replicas, not attempted.
- Tests: `tests/test_union_mbar_per_epoch_bias.py` (bias-formula unit tests, per-epoch-override-vs-global-fallback logic, integration test reproducing chignolin_5 scenario end-to-end via real Parquet/`WindowSnapshot` fixtures), `tests/test_secondary_cv_regime_split.py` (regime detection from `run_manifest.json`, dominant-epoch selection, unresolvable-epoch fallback, integration test with deliberately different per-regime `cv2` distributions proving split output not blended).


## `plot_adaptive_diagnostics.py`'s `discover_phases` silently dropped a numbered epoch using scheduled (baseline+topup) layout — FIXED 2026-08-05

- Found investigating user report ("something wrong with epoch frame numbers in output figures") on real run (`chignolin_5`) further along than fixes above: `epoch_001` picked up 3 quality-gate-triggered topup extension rounds of own, on top of `final`'s own baseline+topup.
- Root cause: `discover_phases`'s numbered-epoch loop only accepted *flat* `epoch_NNN/samples/` layout (`epoch_dirs = sorted(d for d in ap_dir.glob("epoch_*") if d.is_dir() and (d/"samples").is_dir())`). `run_scheduled_adaptive_epoch`'s baseline+topup_* sub-run layout (`gareus/adaptive_production.py`) — previously believed (per 2026-07-18 fix above) to only apply to `final` — also applies to any numbered epoch once `policy.allocation_scheduler` active for it. `epoch_001` here had no top-level `samples/` (only `epoch_001/baseline/samples/`, `epoch_001/topup_*/samples/`), so failed flat-layout filter, silently skipped — timeline figure jumped from `"Epoch 0 (initial)"` to `"Final Baseline"`, missing epoch_001's baseline + 3 topups: **61% of run's real samples (5.05M of 8.18M), absent from every phase-based figure.**
- Second, compounding bug same function: `final`'s (now, same code path, any numbered epoch's) topup sub-phases sorted ascending by `topup_NNN_MMMMM` dir name's step-count suffix, assuming cumulative/creation-order marker. Isn't — `MMMMM` = that topup segment's own *extra-step duration* (`run_scheduled_adaptive_epoch` groups per-call by how many additional steps deficiency group still needs beyond baseline). Quality-gate extension loop re-invoking same epoch with shrinking remaining gap produces *decreasing* `MMMMM` values over successive real, chronologically-later rounds — confirmed chignolin_5's `epoch_001`: `topup_001_34794000` (mtime 00:13, first) → `topup_001_25733000` (mtime 04:04) → `topup_001_18937000` (mtime 07:55, last). Ascending suffix sort = *exact reverse* of true creation order whenever phase gets >1 extension round.
- Fix: `discover_phases` now falls back to same baseline/topup_* sub-run discovery for *any* numbered epoch lacking flat `samples/` dir, via new shared `_discover_subrun_phases(base_dir, label_prefix)` (used for both numbered epochs and `final`, replacing `final`-only inline block). Sort key changed from step-count suffix to dir `mtime` — true chronological order regardless of how remaining-gap value moves round to round. `fig_topup_targeting`'s two independent topup-sort call sites (`topup_*_windows.csv` glob, its own `subdirs` walk of `final/`) fixed same way, for consistency/robustness even though `final` only had one topup round here (not yet visibly broken, same latent bug).
- Real-run verification (`chignolin_5`): phase count 3 → 7 (`epoch_000, epoch_001/baseline, epoch_001/topup_001_34794000, epoch_001/topup_001_25733000, epoch_001/topup_001_18937000, final/baseline, final/topup_001_375000` — printed in that now-correct chronological order); `adaptive_fig1_phase_coverage.png`, `adaptive_fig3_topup_timeline.png` regenerated end-to-end, visually confirmed: Panel A's "Cumulative Samples per State across Phases" line now climbs smoothly across all 7 real phases (previously flat 3-point line skipping epoch 0 to final) with topup durations correctly decreasing (+139.2 ns → +102.9 ns → +75.7 ns), matching shrinking-remaining-gap extension-loop pattern.
- Not affected: `analyze_gareus_mbar.py`'s separate `_analyze_epoch_cv_exploration` (numbered-epoch loop already tries flat layout first, falls back to aggregating `sorted(epoch_dir.iterdir())` sub-dirs per epoch) — discovers epoch_001 correctly already. Within-epoch topup concat order doesn't matter there, aggregates each *whole* numbered epoch into one pooled entry rather than treating each topup as own timeline point.
- Tests: `tests/test_plot_adaptive_diagnostics.py` — `test_discover_phases_finds_scheduled_layout_for_numbered_epoch` (reproduces missing-epoch_001 case), `test_discover_phases_orders_topups_by_creation_time_not_step_suffix` (reproduces chignolin_5 decreasing-suffix scenario via `os.utime`, asserts mtime order wins over suffix-value order).


## `_prepare_adaptive_merged_traj_dir` collapsed a phase's own internal resume segments, discarding most coordinate data — FIXED 2026-08-05

- Found investigating why chignolin native-hairpin 2D FES (and Rg/PCA, sharing same trajectory-alignment code) looked far noisier than main CV1 PMF. Initial read: only 856,655 of 9,671,833 samples (8.9%) had matched trajectory frame — first assumed ordinary `--traj-interval` sparsity (writing coords less often than CV1 logged), but `report_interval`/`traj_interval` both 150 steps in this run's config, direct XTC-frame-timing measurement confirmed trajectories written every 150 steps as configured. 8.9% needed different explanation.
- Two real, smaller-scale issues confirmed along way but **not** dominant cause: (1) `epoch_001/baseline`'s Parquet segments had leftover, un-deleted `chunk_*.parquet` alongside already-consolidated `data.parquet` covering same step range (`ParquetSampleWriter._consolidate`, `gareus/store.py`, correctly deletes chunks after merging — but second `ParquetSampleWriter` evidently reopened against same `seg_NNN` dir, chunks never consolidated/cleaned), producing ~24% exact-duplicate CV rows in that phase; (2) one XTC segment per replica (`resume_from_011997844`) genuinely corrupted ("Malformed XTC... 0 atoms"). Neither explained more than few percent of gap.
- Root cause: `_prepare_adaptive_merged_traj_dir` (used whenever `d.prod_dir/"replica_trajectories"` doesn't exist directly — true for every multi-phase adaptive-production run, real trajectories live under each phase's own subdir) symlinks every phase's trajectory files into one dir so segments merge in chronological phase order. Deduplicated symlink names using set keyed **only by replica stem** (`base_written`), any file past first seen for given replica within phase fell into `else` branch whose link name keyed **only by `epoch_idx`** — no term for which segment within phase. Phase interrupted+resumed more than once (SIGTERM + auto-resume writes fresh `replica_NNN_resume_from_<local_step>.xtc` each time, independent of phase) had all later segments collide on identical link name; only first-processed survived, rest never made it into merged dir.
- Confirmed on chignolin_5: `epoch_001/baseline` alone has 4 real trajectory segments per replica (1 base + 3 internal resumes, `resume_from_003736350`/`007976400`/`011997844`) — buggy merge kept only 1 of 4 per replica in that phase. Measured before/after: total valid frames in merged dir 3,348,831 → 8,540,443 (2.55x) once every segment preserved; trajectory-derived matched-sample count used by chignolin-FES/Rg/PCA 856,655 (8.9%) → 3,630,323 (37.5%) — 4.24x improvement, without touching alignment math.
- Fix: link names now key off `epoch_idx * STEP_STRIDE + local_resume_start`, `local_resume_start` parsed from segment's original filename (0 for phase's true base file, matching `_MERGED_TRAJ_RESUME_RE`) — unique per (phase, segment) pair regardless of internal resume count. Composes correctly with `_adjusted_steps_for_merged_traj`'s existing `+ src * STEP_STRIDE` per-phase windowing (unchanged) since local offset folds into same global scheme. Also rebuilds merged dir from scratch each call (`shutil.rmtree` before recreating) so stale merge from before fix, or from run whose phase list changed, never leaves incorrect leftover links — previous version only added missing links, never corrected existing ones.
- Remaining ~62% gap after fix real, not (as far as measured) further bookkeeping bug: some fraction genuinely-corrupted XTC segments (confirmed at least one, not swept across whole run), some ordinary `--traj-interval` frames whose trajectory file never written before interruption, still-outstanding duplicate-consolidated-chunk issue (~24% in one phase checked) inflates Parquet-side denominator independent of trajectory availability. Not chased further; fix scope = merged-dir symlink collision specifically.
- Function had zero prior test coverage.
- Tests: `tests/test_merged_traj_dir_multi_resume.py` — phase with multiple internal resume segments all get distinct links (reproduces real chignolin_5/epoch_001/baseline shape), 0-byte files still skipped, stale leftover links from prior run discarded on rebuild.


## MBAR bias reconstruction silently fabricated bias for missing/masked secondary-CV samples — three-layer bug chain, FIXED 2026-08-15

Found during Plan A3 (MBAR-analysis modularization — relocating MBAR solver/bias-reconstruction domain) as real correctness fix, not relocation. Three separate, chained root causes, each hiding next:

1. **`gareus/query.py`'s `reconstruct_bias_matrix` fabricated "0 deviation" for NaN sample `cv2`.** Window-side guard (`"center2" in w and "k2" in w`) checked dict-key *presence* only — never that `center2`/`k2` finite, or `k2 > 0` — so no-restraint window (`center2=nan, k2=nan`, or negative `k2`) still got CV2 term applied, poisoning/corrupting that window's whole bias column. Separately, sample-side code used `np.where(np.isfinite(c2), c2-center2, 0.0)`, treating any sample with unmeasured/NaN `cv2` as sitting exactly on restraint target (fabricated "on-target" bias of 0), rather than excluding. Fixed: window-side guard now requires `math.isfinite(center2) and math.isfinite(k2) and k2 > 0.0`; sample-side fabrication removed, so NaN sample `cv2` now correctly produces NaN in that (sample, window) bias-matrix entry, propagating to exclusion by `clean()`. New 9-test suite: `tests/test_query_reconstruct_bias_matrix_nan_guard.py`.

2. **That fix had *zero real-world effect*, because DuckDB silently unmasks null `cv2` to arbitrary fill value before `reconstruct_bias_matrix` sees it.** `fetchnumpy()` returns `numpy.ma.MaskedArray` for any Parquet column with real SQL NULL — mask correctly marks nulls, but underlying `.data` holds arbitrary fill value (observed: `0.0` for float32 column). Two of codebase's loaders (`gareus/mbar_analysis/loaders.py`'s `load_parquet`, `gareus/mbar_analysis/loaders_union_parquet.py`'s `load_parquet_adaptive_union`) cast `cv2` with bare `.astype(np.float64)`, silently dropping mask, exposing `0.0` as real measured value — worse than fix #1's original bug, since `0.0` isn't even "no restraint" signal, it's arbitrary wrong number fed into bias formula. Root cause one layer deeper: `gareus/query.py`'s `_concat_numpy_dicts` (used internally by `load_samples`, called by both loaders to get `samples['cv2']`) merged per-segment DuckDB result dicts with blanket `np.concatenate`, silently dropping `MaskedArray`'s mask — reproduced even for single-segment (1-element list) run, not just multi-segment merges. Meant `gareus.query.export_analysis_arrays_npz`'s already-mask-aware `.filled(np.nan)` cast ("reference correct" pattern cited above) *also* inert in practice, since it too calls `load_samples` first — mask already gone. Fixed: `_concat_numpy_dicts` now uses `np.ma.concatenate` for any column DuckDB returned as `MaskedArray` (plain `np.concatenate` kept for ordinary columns, avoiding unneeded mask allocation on multi-million-row hot path); new shared helper `gareus.mbar_analysis.data._fill_masked_nan(arr)` converts possibly-masked array to plain float64 with NaN at masked positions, both loaders route `cv2` through it instead of casting directly.

3. **Fixing #2 broadly (preserving masks for every column, not just `cv2`) introduced new regression**: `gamd_boost_total`/`gamd_boost_dihedral` genuinely all-NULL for every sample of non-GaMD/plain-umbrella run (`gareus/production.py`'s `extract_gamd_boost_kj` returns `None` for non-GaMD integrator). Once `_concat_numpy_dicts` preserved masks generally, `Data.boost_kj` for such run became live, fully-masked `numpy.ma.MaskedArray` — `analyze_gareus_mbar.py`'s `run_pmf_and_gamd_boost_report` (main PMF/GaMD-boost report path, run for essentially every real analysis) crashed `ValueError: output array is read-only` at `np.nanstd(d.boost_kj)` call, defeating short-circuit guard (`bool(bs.get('available')) and np.nanstd(...) > ...`) meant to skip it — because `boost_stats`'s masked-boolean-indexing (`boost[np.isfinite(boost)]`) doesn't filter fully-masked array as it looks like it should, so `available` came back `True` instead of `False`. Fixed routing `boost`, `boost_dih`, and (for uniformity, though not provably reachable-null today) `potential` through same `_fill_masked_nan` helper, in **both** `loaders.py` and `loaders_union_parquet.py` (latter had own distinct 2-step version of regression: local `boost = np.concatenate(all_boost)` re-denatured already-correctly-masked per-epoch array before reaching `Data`). `boost_stats`'s masked-indexing bug deliberately left unpatched: audited every `Data`-constructing call path (`load_parquet`, `load_parquet_adaptive_union`, `load_npz`, `load_csv`, `load_union_npz`, `load_epoch_csv_adaptive`), confirmed only first two can produce masked `boost_kj`, both now fixed — bug real but currently unreachable; revisit if future loader adds another masked-array-producing path.

- **Results-changing caveat, same class as 2026-08-04 union-MBAR per-epoch-bias fix above**: run with null `cv2` samples in states genuinely secondary-restraining (`k2 > 0`) now has those samples correctly *excluded* from MBAR rather than silently included with fabricated bias — changes `pmf_summary.json`'s numbers for such runs; don't treat prior results comparable without re-running `analyze_gareus_mbar.py`. **Pure CV1-only runs NOT affected numerically** — window snapshots omit `center2`/`k2` entirely (`gareus/production.py`, when `secondary_cv_centers is None`), so CV2 branch never ran, before or after (confirmed: `u_nk` computed from `cv2=all-NaN` vs `cv2=all-0.0` bitwise identical for CV1-only window set). For those runs only `Data.cv2` changes (`0.0` → NaN), removing spurious delta-function at `cv2=0.0` from CV2-facing output (`analyze_secondary_cv_pmf`, `analyze_cv1_cv2_2d_fes`) — not PMF-numbers change.
- Whole-tree grep for every other `cv2_raw`-cast-shaped pattern done before closing: similar-looking cast in `compare_gareus_runs.py` checked, excluded — reads from NPZ source (`_load_merged_arrays`), `np.load` never returns masked array, so not vulnerable.
- Tests: `tests/test_query_reconstruct_bias_matrix_nan_guard.py` (9, fix #1), `tests/test_loader_masked_cv2_nan.py` (13: `_fill_masked_nan`/`_concat_numpy_dicts` unit tests, real-Parquet-fixture end-to-end tests for `load_parquet`/`load_parquet_adaptive_union` proving `Data.cv2`/`u_nk` show NaN not `0.0`, null-`cv2` samples correctly excluded when window secondary-restrains, non-GaMD `boost_kj` crash-regression guard from fix #3).
- **Related, currently-unreachable finding from relocating callers onto `reconstruct_bias_matrix`** (Plan A3's Task 3, `gareus/mbar_analysis/bias.py`'s `_compute_u_nk_analytical`/`_reconstruct_union_bias_block`, both now thin delegations to `reconstruct_bias_matrix` instead of duplicating formula): `reconstruct_bias_matrix`'s CV2 guard is `cv2_arr is not None and "center2" in w and "k2" in w`. Pre-relocation `_compute_u_nk_analytical` had no `cv2=None` handling — passing `cv2=None` raised `TypeError` on `cv2 - sec_c`. Post-delegation, `cv2=None` with secondary-restrained window silently drops CV2 term instead of crashing — same bug class as fabrication bug above, in reverse (loud crash → silently-wrong), but not reachable via any current caller: `Data.cv2` non-Optional field (always NaN-filled, never `None`, per `gareus/mbar_analysis/data.py`), `loaders_union_parquet.py`'s `cv2_epoch` always falls back to all-NaN array rather than `None`. Not fixed — flagging in case future caller passes literal `None` for `cv2`.


## Auto-dropped umbrella windows never reflected in `epoch_window_map.csv` — 15% of campaign's samples attributed to wrong state — FIXED 2026-08-25

Root-caused from user report that `RUNS/chignolin_6`'s MBAR base ESS was 0.74% (health FAIL). Full investigation, evidence tables, residuals: `docs/chignolin_6_low_ess_root_cause.md`.
