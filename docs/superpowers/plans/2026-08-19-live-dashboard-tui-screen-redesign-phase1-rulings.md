# Phase 1 execution record — rulings, parked findings and deferred minors

Companion to `2026-08-19-live-dashboard-tui-screen-redesign-phase1.md` (the plan) and
`../specs/2026-08-19-live-dashboard-tui-screen-redesign-design.md` (the spec).

This is the decision record from executing the plan: 14 tasks, each with its own review and
fix rounds, then a whole-branch review, one fix wave and one scoped re-review. Every entry
below is a decision taken during execution rather than something the plan specified — most
are defects found in the plan's own text or code, ruled on so execution could continue.

They are preserved here because the working ledger they came from lives in a git-ignored
scratch directory that is deleted when the plan completes. Each ruling states what was
decided, why, and what it costs if the decision was wrong.

## Rulings

- **R1 — `Panel.tail` (a fixed string set by the producer) cannot express spec §5.3's severity composition, because how many lines get hidden is decided later by the allocator, not by the panel. Replaced `tail: str` with `line_statuses: tuple[str, ...]` (one opaque label per line) and made `trim_panel` compose the tail from the hidden slice via a new `_composition_tail`. Task 6's `tail_summary(statuses[len-1:])` call was incoherent for the same reason and is removed.** — Why: delivers the spec requirement instead of an approximation, and keeps `tui_screen` domain-free (labels are plain strings). — Cost if wrong: Task 1 and Task 6 carry one extra field and one extra helper; reverting to a plain count tail is a small, local edit.
- **R2 — Task 8's test helper passed `now=5000.0` while the context measured elapsed time from the logger's real `start_wall`, so `elapsed_s` was 0, throughput NaN, and the "GPU-day" assertion unsatisfiable. Added a fixed `NOW = 1_700_000_000.0` plus an explicit `eta_start_wall = NOW - 6h` to the test `dashboard_info` (Tasks 8 and 14).** — Why: a test that cannot pass is worse than no test; the fixed clock also keeps golden frames deterministic. — Cost if wrong: only test-harness values change; no production behaviour depends on them.
- **R3 — Both Task 12 and Task 14 claimed the edit to `tests/manual_render_dashboard_frame.py`. Task 12 owns the edit (it is the task that deletes the method the harness calls); Task 14 only re-runs it.** — Why: the harness must not be broken between tasks. — Cost if wrong: none; a duplicate edit would have been a no-op.

- **R7 — `compose_rows` used `usable = max(40, term_w - 2)` as the literal render width, so every terminal narrower than 42 columns rendered boxes wider than the terminal (reviewer measured 40 columns at term_w=30/35/40). The `max(40, ...)` clamp is an inherited `gareus/tui.py` convention and stays for *threshold* arithmetic, but the widths handed to `_panel_lines` are now clamped to `term_w - 2` (floor 18, which is `_panel_lines`'s own minimum) in both the stacked and the single-panel paths. - **R8 — the allocator priced every row as `max(body) + 4` (side-by-side sharing one border set), but the stacked path renders `sum(body) + 4n`. The reviewer measured a 2-panel row allocated 6 lines rendering 12 when stacked, so a narrow *and* short terminal could exceed its body budget — defeating the "fits by construction" guarantee that is this design's entire point. `allocate_rows` gains an optional `term_w`; when supplied it prices a row by the layout that width will actually produce. Default `None` preserves Task 1's behaviour and its 18 tests. Task 11's `render_screen` must pass `term_w` — carried into its dispatch.** — Why: pricing that does not match rendering is not a guarantee, it is a coincidence. — Cost if wrong: one optional parameter and a branch in row pricing; reverting is local.
- **R9 — Task 14's fit matrix started at 70 columns, where a two-panel row still fits side by side, so it never exercised the stacking path both R7 and R8 live in. - **R10 — Finding 2's pricing arithmetic landed correctly but its wiring did not: `allocate_rows` returns ONE scalar body per row and `compose_rows` applies it to EVERY panel, which is right for side-by-side columns and wrong for stacked blocks. Composition must SPLIT a stacked row's allocation: n panels sharing a row allocated B body lines have `B + PANEL_CHROME_LINES - PANEL_CHROME_LINES*n` body lines to divide, which reduces exactly to `sum(min_lines)` at the priced minimum. The regression test must use panels whose content EXCEEDS min_lines, or truncation never happens and the test pins nothing (the delivered one used len(lines) == min_lines and passed either way).** — Why: pricing that matches rendering is worthless if composition then spends the budget n times over. — Cost if wrong: the arithmetic is a one-line derivation checkable against the priced minimum; over-splitting would under-fill a row rather than overflow it.
