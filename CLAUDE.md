## Pep-GaMD (`--gamd-boost-type pep-gamd-lower-dual`) — boost only the peptide

- Stock gamd-openmm dual boosts are structurally entangled with the umbrella: the Total channel binds to bare `energy` (all groups) at `gamd/stage_integrator.py:224`, and the `DUAL_DEPENDENT_GROUP_TOTAL` velocity update (`gamd/langevin/base_integrator.py:463-474`) applies **only** `f0` and `f<dihedral>`. Moving a force to another group drops it rather than unboosting it — which is why `set_all_forces_to_group(0)` was load-bearing and why C1 could not be fixed by regrouping.
- `gareus/pep_gamd.py` adds `PepGaMDLowerDualIntegrator` (subclass of gamd-openmm's dual `LowerBoundIntegrator`, built lazily so the module imports without gamd) and the partition: an auxiliary water-only `NonbondedForce` named `PepGaMDWaterOnlyNonbonded` in group 1, peptide q/ε and peptide exceptions zeroed, PME parameters pinned. `V_pep = energy0 − energy1 + energy2`; applied force `(f0−f1)·FSF_T + f2·FSF_T·FSF_D + f1 + (f−f0−f1−f2)`. OpenMM's CustomIntegrator allows one force group per computation step, so each `fN`/`energyN` is copied into a per-DoF/global intermediate first.
- **Invariant:** the auxiliary force must only exist in Systems driven by the Pep-GaMD integrator. It is added inside `make_gamd_integrator` (idempotent, found by name); `make_cmd_integrator(..., system=)` excludes group 1 with `setIntegrationForceGroups` when the system carries it (the cMD recon builds a plain integrator on a system that `_gamd_boost_group_targets` has already partitioned). The integrator's own cMD stages (`_add_conventional_md_update_step`) are overridden for the same reason.
- Recon and epoch recalibration measure boost targets via `boost_target_energy_kj(context, gid, unit, total_groups=total_energy_groups_for_args(args))` — the Total channel's groups are a property of the **boost type**, never of the stepping integrator (the cMD-kind recon steps a plain Langevin integrator on an already-partitioned system); stock types keep the old all-groups behaviour. `threshold_and_k0` strips the `pep-gamd-` prefix before its lower/upper dispatch. Recorded `potential_kj_mol` excludes group 1 (`physical_energy_groups_for_args`). `prepare_pep_gamd_args(args, topology)` runs right after the production base system is built and stores `args.pep_gamd_peptide_atoms`; `build_pep_gamd_integrator` refuses to run without it.
- PME parameters are pinned from OpenMM's own formula (`pme_parameters_from_tolerance`: `α = √(−ln 2τ)/r_c`, `grid = ⌈2αL/(3τ^{1/5})⌉`), verified against `getPMEParametersInContext` on the Reference platform. Do **not** pin via `getPMEParametersInContext` on the CPU platform: after a Context holding two `NonbondedForce`s has been freed, every later CPU-platform call of that method in the process throws `std::bad_cast` (energies stay correct; only the introspection breaks). Reproduced 2026-09-06 on OpenMM 8.5.1.
- Tests: `tests/test_pep_gamd_boost.py` (partition structure, idempotence, Custom-force-in-group-0 rejection, an **independent oracle** — the auxiliary force reproduces a peptide-deleted water-only system's energy to <0.05 kJ/mol — PME formula match, and integrator identities: cMD stage and k0=0 production stage give bit-identical trajectories against an all-zero auxiliary, Total channel reads `V_pep`, statistics blind to a 5e4 kJ/mol/nm² umbrella), `tests/test_pep_gamd_wiring.py` (energy helpers, cMD exclusion, dispatch, CLI). Shared fixture in `tests/pep_gamd_fixture.py` (GA dipeptide, 2.4 nm TIP3P, ~1,400 atoms, CPU-minimised).
- **gamd-openmm quirk that makes one-step tests vacuous:** the very first `step()` of a fresh Context moves no atom (stock integrators too — traced on a two-particle system, `|dx| = 0` at stepCount 1, normal motion from step 2). Any test that compares trajectories or checks force algebra must warm up one step, re-seat positions/velocities, then measure — and assert that atoms moved. The Pep-GaMD tests do (`_one_step_positions`, `_assert_moved`).
- Not yet done: a pilot measuring σ_V(pep) vs σ_V(total) and the per-step cost of the second PME; helptext has the method section, the methods databank card `gamd-boost-calibration` still needs a follow-up.

## λ ladder over Pep-GaMD boost strength — new rung dimension on top of the umbrella grid

- State grid is now (window, λ): every umbrella window is replicated at a small set of boost strengths λ_k ∈ [0,1] (`gamd_lambda` on `WindowState`/window-CSV rows), so exchange walks a 2D window×rung grid. λ is set at build (`production.py:5843`, copying the shared-setup calibrated globals into each fresh replica), at every accepted swap (`production.py:6679-6680`, both replicas involved), and re-derived on resume (`production.py:4470`, inside `load_production_checkpoint`, unconditionally — a partial GaMD-integrator-globals restore must never leave a replica's boost strength mismatched with its resumed window assignment) — all three call `pep_gamd.set_replica_lambda_for_window(integrator, window_index, state_lambdas, k0max_by_channel)`, which moves only `k0_Total`/`k0_Dihedral` (never `threshold_energy`, which stays `Vmax` on both channels independent of λ). (Line numbers as of this task's final commit; they will drift with future edits.)
- The envelope (`Vmax`/`Vmin`/`k0_max` per channel) lives in `shared_gamd_setup_globals.json`, either directly under the run dir (single production run) or under `<run_dir>/global_shared_gamd_setup/` (adaptive-production campaign export) — `gareus.mbar_analysis.ladder.load_pep_gamd_envelope(run_dir)` tries both. It is calibrated once at the shared GaMD setup stage and **never recalibrated mid-campaign**, even when production frames fall outside `[Vmin, Vmax]` on some rung (that only turns the boost off on that frame, it does not invalidate `u_ik`, which is reconstructed from the frozen envelope plus the frame's own stored `v_pep_kj_mol`/`v_dih_kj_mol`).
- `gareus.mbar_analysis.ladder.apply_ladder_boost_to_u(u_nk, v_pep, v_dih, state_lambdas, envelope, beta, meta)` is the ONE place the boost term is ever added to a bias matrix, replacing three hand-rolled copies (`load_csv`, `load_parquet`, `build_union_state_mbar_inputs`) that each carried a slightly different guard. The critical bug it fixed: `load_csv`'s `has_vectors` branch used to add the boost a SECOND time on top of `production.assemble_bias_matrices`'s already-boosted stored bias vectors, double-counting it for every ladder run using `--write-full-bias-csv-vectors`. A sample with a non-finite `v_pep`/`v_dih` now gets NaN (not a silently-fabricated 0.0 boost) in every `gamd_lambda>0` column — exclusion-by-propagation, same convention as `reconstruct_bias_matrix`'s missing-cv2 handling.
- Quoting gate: λ=0-only PMF vs full-ladder PMF, written to `pmf_analysis/pmf_ladder_crosscheck.csv`/`.png` and `pmf_summary.json["ladder_crosscheck"]`; `gareus_report.py:_check_ladder_crosscheck` turns a `"fail"` status into a hard FAIL on the overall verdict (not a warning that could sit inside an otherwise-PASS report) — `"skipped"`/absent both grade NA.
- Schema-evolution fix riding along: `gareus/query.py:_concat_numpy_dicts` used to take its column key set from only the FIRST segment, so a campaign resumed across this deploy (older segments without `v_pep_kj_mol`/`v_dih_kj_mol`/`gamd_lambda` mixed with newer ones that have them) silently dropped the new columns (oldest-first order) or crashed with `KeyError` (reversed order). Now takes the union of keys across all segments and back-fills a fully-masked NaN/null placeholder for a segment missing a key present elsewhere.
- Controller ruling (found by an earlier task's implementer, fixed here): `--resume` never persisted `args.state_gamd_lambdas` itself across a restart; if window_metadata on the resumed path could not supply a per-row `gamd_lambda` either, every replica would silently resume at λ=0 (an all-zero ladder is also the valid "disabled" state, so nothing would complain). `production._reload_state_gamd_lambdas_on_resume(args, out_dir)` reloads it from `run_manifest.json`'s `method_settings["state_gamd_lambdas"]` (written once at campaign start by `provenance._method_settings`, never overwritten by a resume's `update_run_manifest` patches) whenever `args.state_gamd_lambdas` is still unset/empty. **Ordering is load-bearing and was wrong in the first cut, caught by review:** it must be called in `run_gareus` BEFORE `_derive_state_gamd_lambdas` (reload at `production.py:5418`, derive at `:5427`), never after — `_derive_state_gamd_lambdas`'s own fallback-of-last-resort is `[0.0] * n`, a non-empty (hence truthy) list, so a reload placed after it always found `args.state_gamd_lambdas` already "set" and silently never read the manifest on any real run. Placed before `_derive_state_gamd_lambdas` instead, the reload only ever observes `args.state_gamd_lambdas` in its genuine pre-derivation state, and `_derive_state_gamd_lambdas`'s own `existing=` parameter then naturally picks up whatever it restored.
- Still open: per-state λ is inferred by `np.nanmedian` over each state's samples in three loader call sites (`loaders.py` x3, `loaders_adaptive.py:1797`) rather than read from one authoritative source; the crosscheck's tolerance is a fixed default (`DEFAULT_TOL_KCAL`), not the analyzer's own `--pmf-uncertainty` block-bootstrap σ (no bootstrap sigma exists yet at the one call site that would need it); and `samples.csv` is referenced everywhere as the canonical production output (readers, provenance, helptext, resume fallbacks) but no code actually writes a file by that name — production writes `distances.csv` (CSV mode) or Parquet chunks (`ParquetSampleWriter`), never `samples.csv` itself.

## `plot_adaptive_diagnostics.py` — epoch/phase figures were badly wrong

Found by visually inspecting `adaptive_fig1-4_*.png` from an analysis of a real completed run (`chignolin_quicktest`) whose adaptive-production loop stopped after epoch 0 (see the `stop_adaptive` entry above) and was resumed mid-epoch via SIGTERM once. Called from `analyze_gareus_mbar.py` (dynamically loaded, `_diag.run_all(...)`, wrapped in try/except so a failure here only prints a one-line skip message) but all three bugs and their fixes are in `plot_adaptive_diagnostics.py` itself:

1. **`discover_phases` only ever found `epoch_000`.** It looked for baseline/topup_* segments inside a literal `ap_dir/"epoch_001"` directory. The driver always writes scheduled final-phase segments under a separate top-level `ap_dir/"final"` instead, regardless of how many numbered epochs ran (the epoch loop can stop after epoch 0 via its convergence gate — see above — handing the rest of the MD-pool budget straight to `final`). Real run: `epoch_001/` existed but held only a stray planning CSV; `final/baseline`, `final/topup_001_12000`, `final/topup_002_31000` held all the real segments. Result: every "per-phase" figure (1, 2, 3) silently rendered a single panel/degenerate range instead of all real phases. Fixed: generalized to glob all `epoch_*` dirs with a real `samples/` dir (not just `epoch_000`), then separately look under `ap_dir/"final"` for baseline/topup_* children. `fig_topup_timeline`'s and `fig_topup_targeting`'s own `epoch_001`-hardcoded lookups (`epoch_schedule.csv`, `baseline_windows.csv`, `topup_*_windows.csv`) fixed the same way.
2. **Every figure loaded only `path/"samples"/"seg_001"`, silently dropping later segments.** A SIGTERM-interrupted-then-resumed segment writes a *new* segment directory (`seg_002`, ...) rather than appending to `seg_001`. Real run: `epoch_000/samples/` had `seg_001` (200,556 rows, pre-interruption) *and* `seg_002` (2,924,448 rows, post-resume) — the old code was reading 6.4% of epoch_000's real samples and reporting it as the whole phase. Fixed: point `pyarrow.dataset` at the `samples/` directory itself (it discovers all segment subdirectories automatically) instead of hardcoding `seg_001`.
3. **The "Sample Count Grid" heatmap panel (fig 2) was always all-zero.** Its lookup dicts (`p_idx`/`s_idx`) were keyed by the raw unrounded `primary_center`/`secondary_center` floats, then looked up with `round(x, 6)` — `secondary_center` is a continuous CV projection with far more significant digits than that, so every lookup silently missed. Fixed by rounding both the dict keys and the lookup the same way. Extracted into a standalone `_sample_count_grid(state_reg, state_counts)` helper so this is unit-testable without rendering a figure.
4. **CV2 axis labels were hardcoded to `"rama"`/`"rama-map"`** in three places, regardless of the run's actual secondary CV type (this run used `torsion-pca` → `tica-linear`). Fixed with a new `_secondary_cv_label(phases)` helper that reads `secondary_cv` from the *last* phase's `run_manifest.json` (CV2 can switch mid-run; the last phase is where most plotted production weight sits) and maps known types to short display names, falling back to the raw string or `"secondary"`.
- Tests: `tests/test_plot_adaptive_diagnostics.py` (8 tests) — phase discovery finds `final/*` not `epoch_001/*`, generalizes to however many real numbered epochs exist, loads all segments under `samples/` not just `seg_001`; grid math matches high-precision floats; CV2 label mapping/fallback/last-phase-preference.
- Verified end-to-end against the real affected run (`plot_adaptive_diagnostics.py RUNS/chignolin/chignolin_quicktest`, before/after): phase count 1 → 4, epoch_000 point count 10,028 → 156,251 (stride 20; matches the real ~3.13M-sample run), per-window sample bar chart 33,426 (flat, wrong) → 521,199-521,579 (matches `pmf_analysis/window_diagnostics.csv` exactly), grid heatmap empty → populated.

## `--ap-epoch0-step-fraction` — new flag, epoch0:epoch1 was structurally forced 1:3

- `adaptive_production_epoch0_step_fraction` was hardcoded to `0.5` in `gareus/cli.py`'s `_apply_v2_compat_shims`, with no argparse flag reaching it. With `--ap-epochs 2`, the pool's live per-epoch recompute (`gareus/adaptive_production.py`'s `_epoch0_scaled_steps` + the fresh `remaining_ns`-based share for epoch 1) gives epoch 0 exactly **1/4** and epoch 1 exactly **3/4** of the epoch-portion MD-pool budget — not the 1:1 split the "0.5" name suggests. Epoch 0's unused half isn't dropped, it's redistributed to epoch 1 via the pool's live recompute.
- Added `--ap-epoch0-step-fraction` (default `0.5`, unchanged behavior) so this is finally reachable. Set to `1.0` to disable the redistribution and get an even split across epochs.
- Tests: `tests/test_ap_epoch0_step_fraction.py` — confirms the argparse default/override wiring, and reproduces the exact 1/4:3/4 (fraction=0.5) vs 1:1 (fraction=1.0) split math via `_epoch0_scaled_steps` directly.
- Independent of this: the epoch loop used to also stop after epoch 0 entirely regardless of `--ap-epochs`, via the convergence gate (`stop_adaptive`) — see below (now fixed: 2026-07-27). This flag only affects the *ratio* epoch 0 gets when the loop runs a further epoch.

## Adaptive-production epoch loop can stop after 1 epoch regardless of `--ap-epochs` — FIXED 2026-07-27

- Root-caused why a run configured for `ap_epochs: 2` (torsion-pca epoch 0 → tica-linear epoch 1) only ever produced real samples in `epoch_000`, with `epoch_001/` left holding just a stray planning CSV and the rest of the MD-pool budget going straight to `final/baseline` + `final/topup_*`.
- `run_adaptive_production_auto_loop` (`gareus/adaptive_production.py`) runs a convergence gate after every epoch (`status`/`stop_adaptive` computed around line 5288): if there are no errors, no `continue_reasons` (a state below `convergence_min_samples_per_state`, default 50 — trivially cleared by any real epoch — or a proposed add/split action, impossible once already at the window cap), and no warnings, `status="converged"` and `stop_adaptive=True` unconditionally. The loop used to `break` on that regardless of how many epochs `--ap-epochs` still allowed. Confirmed directly: `adaptive_production/epoch_000/adaptive_convergence_gate.json` had `{"status": "converged", "stop_adaptive": true, "continue_reasons": []}`.
- Same pattern independently observed and reported on a different real run (`chignolin_sigma3_2d`): epoch 0 converged trivially, jumped straight to final, and the final phase's own (stricter) quality gate then immediately demanded more discovery epochs anyway via a manual `--extend adaptive` re-invocation — i.e. the early exit didn't even save work, it just meant paying for the final phase twice.
- The tICA CV2 switch itself was **not** at risk from this — it's tied to the tICA refit succeeding at the end of whichever epoch triggers `tica_update_after_epochs`, independent of the adaptive loop's own convergence-based early exit. Confirmed: `final/baseline`, `final/topup_001_12000`, `final/topup_002_31000` all ran with `secondary_cv: tica-linear` in their `run_manifest.json` even though `epoch_001` (the epoch that was "supposed to" be the tica-linear one) never ran.
- Fix: convergence no longer breaks the loop. `run_adaptive_production_auto_loop` now just logs and falls through to the next scheduled epoch; the loop always runs the full configured `adaptive_production_epochs` budget and only proceeds to the final phase once that's exhausted. The adjacent `require_convergence_before_final` check (previously unreachable when converged, since the break fired first) got an explicit `not gate_converged` guard — extracted into `_epoch_loop_missing_convergence(epoch, max_epochs, gate_converged, require_convergence_before_final)` — so a legitimately-converged last epoch doesn't spuriously raise. Tests: `tests/test_epoch_loop_convergence_guard.py` (truth table over epoch/max_epochs/convergence/policy combinations, including `max_epochs == 1` and last-epoch edge cases).
- Note `--ap-*` doesn't currently expose `require_convergence_before_final` at all (`gareus/cli.py`'s `_apply_v2_compat_shims` hardcodes it `False`, same "dropped tuning knob" pattern as `--ap-epoch0-step-fraction` before that flag was added) — so today the `RuntimeError` branch this guards can never actually fire from the shipped CLI. Not fixed here; flagging in case a future `--ap-require-convergence-before-final`-style flag gets added, since the guard's correctness will matter then.

## Union-MBAR reduced-bias matrix was 100% NaN — `gareus_metadata.json` never has a temperature field — FIXED 2026-07-27

- Found on a real multi-day production run (`chignolin_sigma3_2d`): `adaptive_union_mbar.npz`'s `umbrella_bias_kcal_mol_nk`/`umbrella_bias_kj_mol_nk` were 100% finite (sane 0-44 kcal/mol range) but `umbrella_reduced_bias_nk` was 100% NaN despite real `N_k` sample counts (49,044 samples across 25 states) — `adaptive_union_mbar_analysis.json` correspondingly errored with `"no finite samples remain after filtering"`.
- Root cause: `_metadata_beta_1_over_kj_mol` (`gareus/adaptive_production.py`) resolved `beta` by reading `temperature_K`/`temperature_k` from each run directory's `gareus_metadata.json` — but that file only ever contains CV/window bookkeeping (confirmed: 63 keys, zero of them temperature-related, across every subdirectory checked in the real run). So `beta` was `None` for every single merged sample row, `beta_1_over_kJ_mol` was written as `""` throughout the whole campaign, and `build_union_state_mbar_inputs`'s `umbrella_reduced_bias_nk = beta * umbrella_bias_kj` fell into its `np.full_like(..., np.nan)` branch every time.
- Fix: added `resolve_run_temperature_k(run_dir)` to `gareus/io.py` — falls back to `run_manifest.json`'s `resolved_args.temperature_k` / `method_settings.temperature_k` (always populated by `gareus/provenance.py` for every run directory) when `gareus_metadata.json` has nothing usable. `_metadata_beta_1_over_kj_mol` now delegates to it.
- Same root cause also silently affected `gareus/analysis.py`'s `_ensure_analysis_arrays_npz` (used when reconstructing `analysis_arrays.npz` from Parquet for resumed/incomplete runs): it read the same never-populated `gareus_metadata.json` field but, unlike the adaptive-production path, defaulted straight to `300.0 K` instead of failing — silently wrong (not NaN) for any run not actually at 300 K. Fixed to use the same `resolve_run_temperature_k` helper; only defaults to 300 K (with a printed warning) if that helper genuinely finds nothing.
- Tests: `tests/test_resolve_run_temperature.py` (the shared helper directly), `tests/test_beta_metadata_fallback.py` (the adaptive-production wrapper, kept as an integration-level check).

## `--sigma0d` is a no-op for single-boost GaMD types (only `--sigma0p` matters)

- Root cause of a real finding on the chignolin quicktest run: its `gamd:` section set `sigma0d: 2.0` under `boost_type: lower-dihedral`, expecting that to control the boost target. It does nothing there. Traced into the upstream `gamd` package (`gamd/integrator_factory.py`): `get_integrator`'s `"lower-dihedral"` branch (and every other single-boost type) calls `create_lower_dihedral_boost_integrator(..., sigma0p)` — passing only `sigma0p`. That function's signature is `(..., sigma0=6.0*kcal)`; `sigma0d` isn't even a parameter. `sigma0d` only reaches anything for the *dual*-boost integrators (`lower-dual`, `upper-dual`, and their `*-nonbonded-dihedral` variants), which do take both.
- Confirmed in the quicktest run's own recorded state: `run_args.json` had `sigma0d_kcal_mol: 2.0` (set) and `sigma0p_kcal_mol: 6.0` (untouched default), and `global_shared_gamd_setup/shared_gamd_setup_globals.json` shows the calibration actually targeted `sigma0_Dihedral: 25.104 kJ/mol` — exactly 6.0 kcal/mol, i.e. sigma0p, not the intended 2.0.
- Consequence: 6.0 kcal/mol was too large a target for DPETG's dihedral-energy dynamic range (calibrated `Vmax-Vmin ≈ 129 kJ/mol` for a 5-residue/8-torsion system). `k0` saturated at its ceiling (1.0) and stayed there even after the epoch-0 real-sampling recalibration (`recalibration_history`: `k0_before == k0_after == 1.0`) — a structural ceiling, not calibration noise — achieving only `sigmaV ≈ 11.5-11.7 kJ/mol`, under half the target. A maxed-out, unmoderated boost applied to DPETG's fast multi-basin flickering (Poincaré map: median recurrence 0.1-0.2 ns) produced a strongly non-Gaussian boost distribution: `anharmonicity_score = 1.11` (skew 0.96, excess kurtosis 1.13), flagged HIGH by the pipeline's own PMF analysis (`analyze_gareus_mbar.py`, threshold >1.0).
- Fix: `gareus/cli.py`'s `_validate_gamd_args` (new, called from `parse_args` alongside `_validate_contact_args`) warns when `--sigma0d` is set to a non-default value but `--gamd-boost-type` is one of the single-boost types (`gamd-cmd-base`, `lower-total`, `upper-total`, `lower-dihedral`, `upper-dihedral`, `lower-nonbonded`, `upper-nonbonded`) — so this exact mistake surfaces immediately instead of silently mis-calibrating. Tests: `tests/test_gamd_boost_default.py` (warns for all 7 single-boost types with `sigma0d` set, doesn't warn for the 4 dual-boost types or when `sigma0d` is left at default).
- `RUNS/chignolin/chignolin_quicktest.yaml` fixed: `sigma0d: 2.0` → `sigma0p: 2.0` (the parameter that actually governs `boost_type: lower-dihedral`).
- **Not yet fixed**: `RUNS/chignolin/chignolin.yaml` (the real 10-residue production config) has the *identical* pattern — `gamd: sigma0d: 2.0` under `boost_type: lower-dihedral`, `sigma0p` unset (defaults to 6.0). Every past production run using this config (chignolin_2d_run5/7 etc.) was very likely calibrated against the same accidental 6.0 kcal/mol sigma0p target, not the intended 2.0. Left untouched pending a decision — chignolin's dihedral-energy dynamic range (more torsions, bigger system) may or may not actually saturate at 6.0 the way DPETG's did; that needs its own calibration data before picking a new number, and retroactively changing it affects comparability with prior runs.

## `-hh` is now an auto-numbered, pageable, jumpable encyclopedia

- `gareus/helptext.py`'s `-hh` used to be a single wall of text with two colliding hand-numbered topic schemes (`0.x` methodology walkthrough, then a `1.`-`17.` reference list — with `13.`, `14.`, and `16.` each reused for two different topics). Fixed at the root: topic numbers are no longer hand-authored. `_parse_encyclopedia` scans the same `Title\n----`-underline heading convention already used throughout the prose (regex `_HEADING_RE`, filtered by underline-length match) and assigns sequential numbers at render time, so the TOC can never drift out of sync with the text again — add/reorder/remove a heading and the numbering just follows.
- `render_encyclopedia_help(parser, encyclopedia_text, topic=None, color=None)` in `gareus/helptext.py` is the shared builder: banner + auto TOC + all topic bodies + `parser.format_help()`. `heavy_help_text` (gareus's own `-hh`) is now a one-line wrapper around it. `gareus/energy_decomposition.py`'s separate `-hh` (`_EnergyDecompHeavyHelpAction`) was ported to the same builder instead of its own hand-rolled dump, so both heavy-help surfaces in the package now look and behave identically ("unite tui design completely").
- `-hh` took an argparse `nargs=0` flag before; now `nargs="?"` (`metavar="TOPIC"`), so it accepts an optional topic:
  - `gareus -hh` — full encyclopedia (banner + TOC + every topic + full flag list).
  - `gareus -hh list` — just the table of contents, no paging.
  - `gareus -hh 8` — jump straight to topic 8 (matched by the auto-assigned number).
  - `gareus -hh <keyword>` — case-insensitive substring match against topic titles; zero matches prints a hint to run `-hh list`, multiple matches lists the candidates and asks for a number instead of guessing.
- New `page_text(text, parser=None)`: when `sys.stdout.isatty()` (interactive terminal) it pipes the rendered text through `$PAGER` (default `less`, with `$LESS` defaulted to `FRX` — raw ANSI passthrough + quit-if-one-screen — only when the user hasn't already set `$LESS`, and without clobbering a custom `$PAGER`'s own args). When stdout is redirected/piped (scripts, `| grep`, CI) it falls straight back to the old plain single print — automation is unaffected, confirmed no automated test or CLAUDE.md smoke command asserts on `-hh`'s exact text. `GAREUS_NO_PAGER=1` forces the plain path even at a tty.
- Section-heading hierarchy in the TOC (indented "sub-topics" under a bold top-level topic) is derived, not hardcoded: a topic is top-level if its original heading looks like bare `"N. Title"`, or — for a document with no such numbering at all, like `energy_decomposition`'s smaller reference — every heading in that document is top-level (checked once per document via `any_level1`, not per-heading) so a flat doc renders flat instead of nesting everything under nothing.
- Color (bold TOC/heading text) is auto-detected from `sys.stdout.isatty()` and disabled by `NO_COLOR`; same detection gates paging, so redirected output is always plain ANSI-free text.
- Deliberately did not touch `GENPEPT.py`'s or `analyze_gareus_mbar.py`'s help — both use plain unmodified argparse `-h` with no `-hh`/encyclopedia concept, out of scope for this change.

## Minimization step-count defaults raised to >= 1000

Every "how many minimization steps by default" argparse default under 1000 raised to 1000 — these were all short defaults tuned for a bigger/older workflow, not a hard physical requirement:

- `GENPEPT.py`: `--implicit-max-iterations` 300→1000, `--explicit-max-iterations` 500→1000, `--bh-initial-min-iterations` 200→1000, `--bh-min-iterations` 150→1000 (basin-hop minimization, part of GENPEPT seed generation).

- `gareus/cli.py`'s `--minimize-iterations` (main NVT-stage system minimization, `gareus/system_setup.py`) was already 20000 — untouched.

**Deliberate exceptions, not touched:**
- `GENPEPT.py --tier-scout-iterations` (default 25) — the scout tier of `--tiered-implicit-min` (off by default) is *designed* to be a cheap fast pre-filter before refining a smaller subset; forcing it to 1000 would make scout as expensive as refine and defeat the tier split's purpose.
- `GENPEPT.py --adaptive-min-chunk-iterations` (default 25) — a convergence-check chunk *granularity* inside the adaptive-minimization loop, not a total step count; the actual total is still governed by `--implicit-max-iterations`/`--explicit-max-iterations` above.

Raised: now just `minimize_iters` (uncapped), matching every other minimization call site in that function — a longer clash-relax before the ramp's first dynamics steps is a stabilizing change, not a destabilizing one, so this doesn't fight the crash-recovery mechanism.

## Torsion-PCA CV2 — `bootstrap_torsion_component` is a count, not an index

- `compute_bootstrap_torsion_pca` (`gareus/tica.py`) previously took `component` as a 1-based index selecting a *single* PCA eigenvector as the `cv2: torsion-pca` direction. Changed: `component` is now a **count** — the top N components (by variance, ranked 1..N) are combined into one unit-norm direction via a variance-weighted linear combination, `coefficient_i = sqrt(variance_i)` then renormalized. CV2 stays a single scalar restraint either way; this just lets that one restraint draw on more than PC1 alone.
- `component=1` is exactly backward compatible: a single positive scalar coefficient doesn't change a normalized direction's identity, so it reduces to the old "PC1 alone" behavior bit-for-bit.
- Default changed `1` → `5` (`--bootstrap-torsion-component`, `gareus/cli.py`; same default fallback in `gareus/production.py`'s `getattr`).
- Important asymmetry: PC1 is *by construction* the single direction of maximum variance, so combining in more components can only match or **reduce** that one direction's own explained variance (`TICAResult.eigenvalue`/`explained_variance_ratio`) relative to PC1 alone — the payoff isn't more variance, it's picking up influence from a mode PC1 alone doesn't see (e.g. a torsion that only loads heavily on PC4).
- Tests: `tests/test_bootstrap_torsion_cv.py::test_bootstrap_pca_component_count_combines_top_n_variance_weighted` verifies the coefficient ratio matches `sqrt(variance_i/variance_j)` exactly and that combined-direction variance is strictly ≤ PC1-alone variance; `test_bootstrap_pca_component_out_of_range_raises` covers the bounds check. `test_bootstrap_pca_fail_closed_on_zero_component_variance` updated for the new semantics (old test's X made requesting component=2 trivially succeed under the new scheme, since PC1 there still carried real variance — not a bug, just no longer a failure case).
- Any cached `<out>/tica/bootstrap_torsion_cv.json` from a run predating this change holds a single raw eigenvector under the old semantics; it's loaded as-is if present (`_ensure_bootstrap_torsion_cv_ready` in `gareus/production.py`), so changing `bootstrap_torsion_component` on a resumed run does nothing until that cache file is deleted and window/seed setup is redone.

## US pull-crash recovery (`gareus/seeding.py`)

- Root cause: contact-CV umbrella pull (`generate_us_starting_states_by_pulling` → `relax_to_window`) can NaN a window's positions on the very first, gentlest ramp sub-stage if that window's target contact combination is sterically close to unreachable given where the secondary CV sits. NaN corrupts CUDA addressing → `CUDA_ERROR_ILLEGAL_ADDRESS` → hard process abort, no auto-recovery, whole run dies (observed twice: `adaptive_feedback_round_01` and `adaptive_production/epoch_000`, both at primary-pull ramp stage 1/5 for a contact-CV window).
- Fix, all in `gareus/seeding.py`:
  - `_run_primary_pull_segment` takes `stage_override` (finer contact ramp than `--contact-us-pull-ramp-stages`, used only for crash retries).
  - `relax_to_window` takes `contact_ramp_stage_override`, threaded through to both its internal `_run_primary_pull_segment` calls (staged-2D distance phase and single-stage path).
  - New `_relax_to_window_recovering(sim, w, direction_label, device_idx)` wraps `relax_to_window`: on any exception, rebuilds a fresh `Simulation` (the raising Context may be CUDA-poisoned — never reused), resets to the equilibrated state, and retries once with a 4×-finer contact ramp (`max(16, contact_us_pull_ramp_stages*4)` stages). If the retry also fails, falls back to `_unpulled_window_row` — the plain unpulled equilibrated state for that window only, tagged `direction: pull_crash_fallback_unpulled (...)`, written to `window_..._CRASHFALLBACK_start.pdb`.
  - All 7 call sites of `relax_to_window` (conformer-seeded concurrent/sequential, independent concurrent, nearest/compact_branch/extended_branch/fallback in the sequential walk) now go through `_relax_to_window_recovering`; the 2D row-base pre-pull loop is wrapped in its own try/except that rebuilds the context and skips that row's warm-start state on failure (individual windows still get attempted below).
  - Quality-control loop (`us_starting_structure_quality.json`) flags any `pull_crash_fallback_unpulled` row as `status: bad` with an explicit warning — one bad window can no longer take down the run, but it's never silently marked "ok".
- One bad steric target now costs one degraded window (flagged `bad` in quality report), not the whole umbrella-window seeding run.

## GENPEPT contact-count bias

- Added `--contact-bias-strength` (default `0.0`, no behavior change) to `GENPEPT.py`: a Metropolis-style soft acceptance bias applied per-conformer in `generate_one`, on top of the existing energy/steric-only filtering.
- `accept_prob = min(1, exp(strength * (ccount - ref)))`. For `strength > 0`, `ref` is the combinatorial max `contact_count` for the sequence/`--contact-min-sep` (so the best-possible conformer is always accepted, lower-contact ones progressively suppressed); for `strength < 0`, `ref = 0` (mirrored, favors fewer contacts).
- Motivation: GENPEPT's per-residue Ramachandran sampling has no compactness/contact bias anywhere (generation, basin-hop, NMA) — confirmed by an A/B test on chignolin (`chignolin_genpept_r3` vs `_r4`, see project memory) where even switching to a hairpin-tuned `diversity_bank_preset` only modestly enriched near-native density without shifting the dominant (open) mode, because per-residue sampling stays uncorrelated across residues.
- `ref` is a loose combinatorial ceiling, often far above what's actually reachable — start with small `strength` (0.05-0.3). Values near/above 1.0 can crush acceptance to near-zero and exhaust `--n` before enough candidates are found (reproduced directly: `strength=1.0` on chignolin with `--n 4000` raised `RuntimeError: Only 0 all-atom-valid candidate seeds found`; `strength=0.15` with `--n 8000` worked and shifted mean `contact_count` from 3.92 to 6.01 on a 300-candidate pool).
- Applied consistently in both `generate_candidates` (initial pool) and `generate_adaptive_frontier_proposals` (explore-loop proposals) via the shared `GenConfig.contact_bias_strength` field, so explore-loop rounds don't silently bypass the bias.

## Union-MBAR bias matrix used a stale global registry snapshot for every epoch — FIXED 2026-08-04

- Found while answering a question about how `analyze_gareus_mbar.py` handles a mid-run secondary-CV redefinition (torsion-pca → tica-linear tICA auto-switch) for the "united" PMF. Confirmed real and severe on a live run (`chignolin_5`, epoch_000 torsion-pca → epoch_001+final tica-linear).
- Root cause: `load_parquet_adaptive_union` (`analyze_gareus_mbar.py`) reconstructed every sample's reduced bias energy (`u_nk`) using **one static snapshot** of window params — `final_registry_used_for_mbar.csv`/`state_registry.csv` — applied uniformly to a state's samples across *every* epoch. That snapshot reflects a state's *current* `primary_center`/`primary_k`/`secondary_center`/`secondary_k` — but those fields get overwritten in place whenever a state is recentered (e.g. `_apply_tica_centers_to_registry`, `gareus/adaptive_production.py`, which fires on the tICA CV2 auto-switch). Any earlier epoch's samples, collected under the old center, then got their bias energy reconstructed against the new one.
- Measured directly on chignolin_5's real state 0: epoch_000 samples were collected under `secondary_center=-2.1337` (`epoch_000/epoch_window_map.csv`, written once and never touched again); the live registry (used for every epoch under the old code) held `+1.1632` post-switch. For the 115,923 real epoch_000/state-0 samples, mean reconstructed reduced bias energy dropped from 126.25 (buggy) to 2.49 (fixed) — ~124 kT of spurious bias energy per sample, i.e. those samples were getting ≈0 MBAR importance weight in their own generating state. 27/28 registry states got this overwrite when the switch fired.
- Fix: each epoch's own `epoch_window_map.csv` already records the window params that were actually in effect for that epoch — `_load_epoch_task` now also parses `primary_center`/`primary_k`/`secondary_center`/`secondary_k` from it (previously only `state_id` was kept), and the union bias matrix is built **per-epoch-block** using those native params (`_epoch_bias_param_vectors`, `_reconstruct_union_bias_block`), falling back to the global snapshot only for states absent from a given epoch's own map (states born in a later epoch — the one case where the global row is correct and the only option). `beta` resolution moved to a dedicated pre-pass so it's fixed before any per-epoch block is built, rather than resolved lazily mid-loop (previously order-dependent in a way that could, in principle, race a downstream top-level beta fallback against an already-built-but-wrong-beta block).
- End-to-end real-run verification (`chignolin_5`, full `analyze_gareus_mbar.py` re-run, same flags, before vs after): base MBAR ESS 67,198 (1.07% of 6.29M) → 360,438 (5.73%) — 5.4x more effective samples, exactly the expected direction once the ~65-125 kT spurious bias energy stops crushing importance weights for the affected states. PMF span 17.76 kcal/mol (inflated by the corrupted bias energies) → 4.55 kcal/mol. MBAR convergence and window overlap (measured from raw CV samples, not `u_nk`) unchanged, as expected.
- **Any adaptive-production run whose CV2 (or CV1) window params were ever recentered mid-campaign and analyzed through the Parquet union path has a wrong PMF from this bug** — not just runs that hit the tICA CV2 type-switch. Re-running `analyze_gareus_mbar.py` on such runs will change `pmf_summary.json`'s `mbar.base_ess`/`pmf_span_kcal_mol`/`pmf_minimum_cv_A`; do not treat prior results as comparable without re-running.
- Separately, and orthogonal to `u_nk` correctness: pooling raw `cv2` values from two different secondary-CV **projections** (torsion-pca vs tica-linear are different linear combinations of the same raw torsion features, not a recentering of one coordinate) into a single "secondary_cv" axis conflates two different order parameters for any CV2-facing plot. `run_secondary_cv_analyses` now detects a regime change via each epoch/phase's own `run_manifest.json` (`_secondary_cv_epoch_regime_masks`) and splits `analyze_secondary_cv_pmf`/`analyze_cv1_cv2_2d_fes` accordingly: the regime containing the run's *last* epoch/phase ("dominant") keeps the existing unmodified output paths (all its epochs pooled together — correct, since they share one CV2 definition); any earlier, different-regime epoch (e.g. `epoch_000` under torsion-pca before chignolin_5's tICA switch) gets its own output under `secondary_cv_regime_<type>/` instead of being silently pooled into the united plot. Single-regime runs (the overwhelming majority) are entirely unaffected — `_secondary_cv_epoch_regime_masks` returns `None` and the wrapper degrades to the original calls, same paths. This does **not** touch MBAR's `f_k`/weights (already correct after the `u_nk` fix above) — only which samples' `cv2` values get binned together for CV2-facing plots.
- Considered but not built: reprojecting epoch_000's raw torsion features through the final tica-linear model (`project_tica1`) to harmonize pre-switch samples onto one common CV2 axis instead of plotting them separately. Rejected after measuring real coverage: chignolin_5's `epoch_000/tica_obs/dihedral_obs_*.npz` covers only 7,668 of epoch_000's 731,754 real production samples (~1%), concentrated in a narrow 127k-step window near the end of the epoch rather than spread across it — harmonizing off that buffer would produce a "unified" axis that's ~99% NaN for epoch_000, i.e. fabricate the appearance of a fix rather than deliver one. A full-coverage version would need to recompute backbone torsion features from `replica_trajectories/*.xtc` directly (`backbone_dihedral_features` + torsion indices from `tica_state.json`) — a real trajectory pass over ~730k frames × 27 replicas, not attempted here.
- Tests: `tests/test_union_mbar_per_epoch_bias.py` (bias-formula unit tests, per-epoch-override-vs-global-fallback logic, and an integration test reproducing the chignolin_5 scenario end-to-end via real Parquet/`WindowSnapshot` fixtures), `tests/test_secondary_cv_regime_split.py` (regime detection from `run_manifest.json`, dominant-epoch selection, unresolvable-epoch fallback, and an integration test with deliberately different per-regime `cv2` distributions proving the split output isn't blended).

- Found investigating why the chignolin native-hairpin 2D FES (and Rg/PCA, which share the same trajectory-alignment code) looked far noisier than the main CV1 PMF. - Tests: `tests/test_merged_traj_dir_multi_resume.py` — a phase with multiple internal resume segments all get distinct links (reproduces the real chignolin_5/epoch_001/baseline shape), 0-byte files still skipped, stale leftover links from a prior run are discarded on rebuild.

## MBAR bias reconstruction silently fabricated bias for missing/masked secondary-CV samples — three-layer bug chain, FIXED 2026-08-15

Found during Plan A3 (MBAR-analysis modularization — relocating the MBAR solver/bias-reconstruction domain) as a real correctness fix, not a relocation. Three separate, chained root causes, each hiding the next:

1. **`gareus/query.py`'s `reconstruct_bias_matrix` fabricated a "0 deviation" for a NaN sample `cv2`.** The window-side guard (`"center2" in w and "k2" in w`) checked dict-key *presence* only — never that `center2`/`k2` were finite, or that `k2 > 0` — so a no-restraint window (`center2=nan, k2=nan`, or a negative `k2`) still had its CV2 term applied, poisoning or corrupting that window's whole bias column. Separately, the sample-side code used `np.where(np.isfinite(c2), c2-center2, 0.0)`, treating any sample with an unmeasured/NaN `cv2` as if it were sitting exactly on the restraint's target (a fabricated "on-target" bias of 0), rather than excluding it. Fixed: the window-side guard now requires `math.isfinite(center2) and math.isfinite(k2) and k2 > 0.0`; the sample-side fabrication was removed, so a NaN sample `cv2` now correctly produces NaN in that (sample, window) bias-matrix entry, propagating through to exclusion by `clean()`. New 9-test suite: `tests/test_query_reconstruct_bias_matrix_nan_guard.py`.

2. **That fix had *zero real-world effect*, because DuckDB silently unmasks null `cv2` to an arbitrary fill value before `reconstruct_bias_matrix` ever sees it.** `fetchnumpy()` returns a `numpy.ma.MaskedArray` for any Parquet column with a real SQL NULL — the mask correctly marks which entries are null, but the underlying `.data` holds an arbitrary fill value (observed: `0.0` for a float32 column). Two of this codebase's own loaders (`gareus/mbar_analysis/loaders.py`'s `load_parquet`, `gareus/mbar_analysis/loaders_union_parquet.py`'s `load_parquet_adaptive_union`) cast `cv2` with a bare `.astype(np.float64)`, which silently drops the mask and exposes `0.0` as if it were a real, measured value — worse than fix #1's original bug, since `0.0` isn't even a "no restraint" signal, it's an arbitrary wrong number fed straight into the bias formula. The root cause was one layer deeper still: `gareus/query.py`'s `_concat_numpy_dicts` (used internally by `load_samples`, which both loaders call to get `samples['cv2']` in the first place) merged per-segment DuckDB result dicts with a blanket `np.concatenate`, which silently drops a `MaskedArray`'s mask — reproduced even for a single-segment (1-element list) run, not just multi-segment merges. This meant `gareus.query.export_analysis_arrays_npz`'s own already-mask-aware `.filled(np.nan)` cast (the "reference correct" pattern cited above) was *also* inert in practice, since it too calls `load_samples` first — the mask was already gone before either code path got a chance to handle it correctly. Fixed: `_concat_numpy_dicts` now uses `np.ma.concatenate` for any column DuckDB actually returned as a `MaskedArray` (plain `np.concatenate` kept for ordinary columns, to avoid allocating an unneeded mask array on the multi-million-row hot path); a new shared helper `gareus.mbar_analysis.data._fill_masked_nan(arr)` converts a possibly-masked array to plain float64 with NaN at masked positions, and both loaders route `cv2` through it instead of casting directly.

3. **Fixing #2 broadly (preserving masks for every column, not just `cv2`) introduced a new regression**: `gamd_boost_total`/`gamd_boost_dihedral` are genuinely all-NULL for every sample of a non-GaMD/plain-umbrella run (`gareus/production.py`'s `extract_gamd_boost_kj` returns `None` for a non-GaMD integrator). Once `_concat_numpy_dicts` started preserving masks generally, `Data.boost_kj` for such a run became a live, fully-masked `numpy.ma.MaskedArray` — and `analyze_gareus_mbar.py`'s `run_pmf_and_gamd_boost_report` (the main PMF/GaMD-boost report path, run for essentially every real analysis) crashed with `ValueError: output array is read-only` at its `np.nanstd(d.boost_kj)` call, defeating the very short-circuit guard (`bool(bs.get('available')) and np.nanstd(...) > ...`) meant to skip it — because `boost_stats`'s own masked-boolean-indexing (`boost[np.isfinite(boost)]`) doesn't filter a fully-masked array the way it looks like it should, so `available` came back `True` instead of `False`. Fixed by routing `boost`, `boost_dih`, and (for uniformity, though not provably reachable-null today) `potential` through the same `_fill_masked_nan` helper, in **both** `loaders.py` and `loaders_union_parquet.py` (the latter had its own, distinct 2-step version of the same regression: a local `boost = np.concatenate(all_boost)` re-denatured an already-correctly-masked per-epoch array before it ever reached `Data`). `boost_stats`'s own masked-indexing bug was deliberately left unpatched: audited every `Data`-constructing call path (`load_parquet`, `load_parquet_adaptive_union`, `load_npz`, `load_csv`, `load_union_npz`, `load_epoch_csv_adaptive`) and confirmed only the first two can ever produce a masked `boost_kj`, and both are now fixed — so the bug is real but currently unreachable; revisit if a future loader adds another masked-array-producing path.

- **Results-changing caveat, same class as the 2026-08-04 union-MBAR per-epoch-bias fix above**: a run with null `cv2` samples in states that genuinely secondary-restrain (`k2 > 0`) will now have those samples correctly *excluded* from MBAR rather than silently included with a fabricated bias — this changes `pmf_summary.json`'s numbers for such runs; do not treat prior results as comparable without re-running `analyze_gareus_mbar.py`. **Pure CV1-only runs are NOT affected numerically** — their window snapshots omit `center2`/`k2` entirely (`gareus/production.py`, when `secondary_cv_centers is None`), so the CV2 branch never ran either way, before or after this fix (confirmed: `u_nk` computed from `cv2=all-NaN` vs. `cv2=all-0.0` is bitwise identical for a CV1-only window set). For those runs, only `Data.cv2` itself changes (`0.0` → NaN), which removes a spurious delta-function at `cv2=0.0` from CV2-facing output (`analyze_secondary_cv_pmf`, `analyze_cv1_cv2_2d_fes`) — not a PMF-numbers change.
- A whole-tree grep for every other `cv2_raw`-cast-shaped pattern was done before considering this closed: a similar-looking cast in `compare_gareus_runs.py` was checked and excluded — it reads from an NPZ source (`_load_merged_arrays`), and `np.load` never returns a masked array, so that script is not vulnerable to this bug family.
- Tests: `tests/test_query_reconstruct_bias_matrix_nan_guard.py` (9, fix #1), `tests/test_loader_masked_cv2_nan.py` (13: `_fill_masked_nan`/`_concat_numpy_dicts` unit tests, real-Parquet-fixture end-to-end tests for `load_parquet`/`load_parquet_adaptive_union` proving `Data.cv2`/`u_nk` show NaN not `0.0` and null-`cv2` samples are correctly excluded when a window secondary-restrains, and the non-GaMD `boost_kj` crash-regression guard from fix #3).
- **Related, currently-unreachable finding from relocating the callers onto `reconstruct_bias_matrix`** (Plan A3's Task 3, `gareus/mbar_analysis/bias.py`'s `_compute_u_nk_analytical`/`_reconstruct_union_bias_block`, both now thin delegations to `reconstruct_bias_matrix` instead of duplicating its formula): `reconstruct_bias_matrix`'s CV2 guard is `cv2_arr is not None and "center2" in w and "k2" in w`. The pre-relocation `_compute_u_nk_analytical` had no such `cv2=None` handling at all — passing `cv2=None` into it would raise `TypeError` on `cv2 - sec_c`. Post-delegation, `cv2=None` combined with a secondary-restrained window silently drops the CV2 term instead of crashing — same bug class as the fabrication bug above, in reverse (loud crash → silently-wrong), but not reachable via any current caller: `Data.cv2` is a non-Optional field (always NaN-filled, never `None`, per `gareus/mbar_analysis/data.py`), and `loaders_union_parquet.py`'s `cv2_epoch` always falls back to an all-NaN array rather than `None`. ## `gareus/mbar_analysis/pmf.py`'s `_bridge()` branch order doesn't deliver its own stated guarantee — found during Plan A4's final review, NOT YET FIXED (fix gated to whichever future plan touches `run_observable_pmf_convergence`, currently scoped as Plan A6b)

- Plan A4 (relocating 24 PMF/GaMD-cumulant/bootstrap-uncertainty functions into `gareus/mbar_analysis/pmf.py`) introduced a runtime `_bridge()` resolver so a relocated function can call back into names still living in `analyze_gareus_mbar.py` without risking a second, independent copy of the script (`python analyze_gareus_mbar.py <run_dir>` loads the script as `__main__`, not under the importable name `analyze_gareus_mbar` — a bare `import analyze_gareus_mbar` from a relocated module creates a second copy whose globals never see `parse_args()`'s CLI-set mutations). `_bridge()` (`gareus/mbar_analysis/pmf.py:29-64`) is supposed to always prefer whichever copy is already loaded, `__main__` included, "so this never happens" (per the Plan A4 design spec's own stated rationale).
- It happens anyway: `_bridge()` checks `sys.modules.get('analyze_gareus_mbar')` **before** checking `__main__`. Several sibling modules that already landed in earlier plans (`gareus/mbar_analysis/loaders_union_parquet.py`, `loaders_adaptive.py`, `writers.py`, `plotting.py`) do a bare `from analyze_gareus_mbar import ...` — which, under `python analyze_gareus_mbar.py`, registers a *second*, independent script copy under the real module name in `sys.modules`. `loaders_union_parquet.py`'s fires unconditionally during data loading on every adaptive-Parquet run, strictly before any `pmf.py` function is ever called — so by the time `_bridge()` first runs, it matches its own first branch and returns that second, never-`parse_args()`'d copy, never `__main__`. Reproduced directly (script loaded as the `__main__`-shaped copy, a global mutated to simulate `parse_args()`, then the sibling's exact bare import executed): the resolved copy flips from "main copy" to "second copy" the instant that one bare import runs.

## Auto-dropped umbrella windows were never reflected in `epoch_window_map.csv` — 15% of a campaign's samples attributed to the wrong state — FIXED 2026-08-25
